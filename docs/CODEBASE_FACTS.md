### Prefilter API error / no API key is cached as core-only and leaves no audit record (2026-10-09, NOT fixed)

**Hypothesis -- not measured in production.** `DomainPrefilter._call_openai` returns `{}` on any exception
(`constitution/retriever.py` outer `except`) and when no API key is configured (early `return {}`). The caller
then applies core-only **and caches it** (`self._cache[cache_key] = relevant`) for the life of the process, with
no `llm_calls` row and no `DOMAIN_PREFILTER_DOMAINS_REJECTED` event (decision UD2, 2026-10-09: out of scope of the

With the precision prefilter (2026-10-11) a provider rejection of the strict `json_schema` response format would
take this same silent path.

### `init_db` startup race: the in-process loss of the WAL switch is FIXED 2026-10-13 (commit `fix(observability): serialize sqlite wal switch`); cross-process race and the schema-ordering gap remain (observed live 2026-09-10)

**Status 2026-10-13 (scope matters).** Fixed: the *in-process* loss of the rollback->WAL journal switch on a new
file, for every opener of `_get_connection` (`init_db`, the write-queue worker, the lifecycle writers, readers). A
per-file lock now wraps only `PRAGMA journal_mode=WAL` (`moralstack/observability/sinks/sqlite_sink.py:546-574`
registry and `_wal_switch_lock`, `:581-582` the guarded pragma). Key: `os.path.normcase(os.path.abspath(path))`,
lexical, so symlink / 8.3-alias spellings of one file get different locks (accepted limit). `init_db`, its
migrations and its callers are unchanged. **Not fixed**: (1) the same switch racing *across processes* (a UI
process or a second proxy on a new file) — known gap, the lock is process-local; (2) the schema-ordering gap, see
the Future-work hypothesis row below. The text below is the 2026-09-10 observation with its mechanism corrected
on 2026-10-13 (D2/D3).

**Corrections 2026-10-13 (code-read).**

- **D2 — there are more than two `init_db` callers, with different locking:** `moralstack/server/proxy.py:801`
  (startup, unlocked), `:830` (under `_run_row_lock`, `:816`/`:825`),
  `moralstack/orchestration/default_persistence.py:37` (unlocked); also `moralstack/cli/shell.py:301`,
  `moralstack/sdk/wrapper.py:688` and `scripts/benchmark_moralstack.py:2463`, all unlocked (the first two inside
  `try/except: pass`).
- **D3 — the "controller thread vs proxy pre-insert thread" story below cannot happen within one request:**
  `_ensure_request_row` (`proxy.py:408`) completes before `orchestrator.process` (`proxy.py:419`) on the same
  thread, and a second request blocks on `_run_row_lock`. The counterpart that races the first `init_db` is not
  established; the write-queue worker is a candidate only (see the Hypothesis row below).
- The 2026-09-29 caveat "which statement returned `database is locked` is an inference" is supported by the probe
  below for the WAL pragma on this platform (not a Verified fact); for the 2026-09-10 run itself it remains an
  inference. The claim (if read that way) that `busy_timeout` covers the cross-process case is **withdrawn**:
  `busy_timeout` does not apply to the WAL switch on a new file.

**Conditionally verified (probe, platform-dependent — NOT a Verified fact).** Windows 11, Python 3.13.9, SQLite
3.50.4, offline, N threads behind a `threading.Barrier` on a fresh file, pre-fix code: the failures come from
`PRAGMA journal_mode=WAL` (`sqlite_sink.py:581-582` now; `:548` at the base commit) and raise in under 1 s, so the
10 s `busy_timeout` is not applied. A lock around the `init_db` body alone does not cover `init_db` vs a bare
connection (9 `init_db` failures and 15 bare-connection errors in 100 mixed trials); serializing the pragma inside
`_get_connection` gave 0 failures in both scenarios. Whether other platforms or SQLite builds behave the same is a
hypothesis. Locked by `tests/test_observability_wal_switch_lock.py` (B3 serialization pin is deterministic; B1, the
real-mechanism stress test, is probabilistic and opt-in with `-m slow`).

**Observed.** Launching the governed COMPL-AI campaign at T=1.5 (`logs_temp_1.5/strong_reject/moralstack-logs-1`)
printed at startup:

```
observability: init_db failed: database is locked
observability: upsert_request failed: no such table: requests
observability[sqlite]: write_window transaction failed: no such table: session_store_events
observability[sqlite]: write_window isolated failed event_type=session_store.get: no such table: session_store_events   (x6)
```

**Impact, measured rather than assumed: none on that run.** The schema was created moments later by the other
caller and all 13 tables exist; at the time of the check the DB held 41 `requests` rows against 36 finalized
JSONL lines — the DB *ahead*, the 5 extra being requests still in flight. So this is startup noise, not the
head-of-run row loss fixed in `e0dd37b`. A handful of `session_store.get` events emitted inside the window were
swallowed by the best-effort `try/except`.

**Mechanism, as written 2026-09-10 (partly superseded by D2/D3 above).** Two independent callers run `init_db` on the same fresh file with no shared
coordination:

- `moralstack/server/proxy.py:_ensure_run_row` — guarded by a process-local `threading.Lock`
  (`_run_row_lock`), **added by `e0dd37b` on 2026-09-08**;
- `moralstack/orchestration/default_persistence.py:_ensure_db_initialized` — guarded only by the instance flag
  `self._db_initialized` (now `_db_initialized_for`), no lock, and it does not take `_run_row_lock`.

A thread inside `controller.process()` therefore calls `init_db` while the proxy pre-insert thread is already
inside it. Both open a connection through `_get_connection`, which issues `PRAGMA journal_mode=WAL`; on a
newly created file that needs a brief exclusive lock, and the loser gets SQLITE_BUSY. `init_db` swallows it,
returns `False`, and the schema is briefly absent for every other writer. Caveat (2026-09-29): `_get_connection`
opens every connection with `timeout=10.0` and `PRAGMA busy_timeout=10000` before the WAL switch
(`observability/sinks/sqlite_sink.py:546-548` at the time; now `:579-582`), so which statement actually returned `database is locked` is an
inference for that run, not something the code shows (the 2026-10-13 probe supports the WAL pragma only on its own
platform, see above); the fix direction below does not depend on it.

**This is a partial regression from `e0dd37b`**: before that commit there was one `init_db` caller in the
request path, now there are two. The trade is still net positive — the commit removed a real loss of `requests`
rows (21 requests absent from SQLite while present in JSONL) and introduced startup noise that self-heals —
but the noise should go.

**Fix direction (2026-09-10 text; applied 2026-10-13 in a different place).** The original proposal was a lock
around the `init_db` body; the probe showed that does not cover `init_db` vs a bare connection, so the lock was
put around the failing statement (the WAL pragma in `_get_connection`) instead. The sibling defect
(`_ensure_db_initialized` caching a path-agnostic flag) was fixed in the same change (row "`DefaultPersistence`
never re-initializes ..." in Verified facts).

**Repro:** start the proxy with `bench-proxy.py` against a non-existent DB path and send >=2 concurrent
requests; the race is on the first request only.

**Hypothesis — a pinning test of the re-point/`init_db` mechanism is intermittent (2026-10-09, NOT investigated).** `tests/test_server_proxy.py::test_request_row_survives_observability_db_repointing` (added in `e0dd37b`) failed once when run alone and once in a `-x` full run during the 2026-10-09 diff review ("no such table: requests" in the re-pointed DB). Later the same day it passed when run alone, in its whole file, and in two full-suite runs. Trigger unknown: test order, environment state, or the same re-point/`init_db` race. Not reproduced deterministically; not investigated. 2026-10-13: a plausible cause is the `init_db`-vs-bare-connection WAL-switch race described above (the mixed race), and, independently, the schema-ordering gap in the next row; **this stays a Hypothesis** until the test is observed stable after the 2026-10-13 fix.

**Hypothesis — envelopes queued before the first `init_db` on a fresh / re-pointed file can still be dropped with "no such table" (2026-10-13, unmeasured, NOT fixed).** The write-queue worker opens its long-lived connection lazily on the first queued item (`moralstack/observability/write_queue.py:319` -> `_open_worker_connection` `:263-278` -> `_get_connection`), and that connection does not create the schema. The proxy queues a `session_store.get` envelope before its pre-insert (`moralstack/server/proxy.py:399` -> `moralstack/sdk/session_store.py:193-196` -> `moralstack/observability/conversation_events.py:352-360`), while the schema is created only by `init_db`'s `executescript` (`moralstack/observability/sinks/sqlite_sink.py:777`). So an envelope processed before the first successful `init_db` can hit "no such table", which would match the `write_window ... no such table: session_store_events` lines of 2026-09-10. Not measured; the 2026-10-13 WAL-switch lock does not address ordering. Structural fix: ensure the schema in `_open_worker_connection` (separate task).
